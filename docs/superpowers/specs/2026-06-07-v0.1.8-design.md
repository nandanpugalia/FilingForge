# FilingForge v0.1.8 — Design Spec

**Date:** 2026-06-07
**Status:** Approved for implementation
**Theme:** Premium-grade reports everywhere + monetization on + release discipline

v0.1.8 bundles three independent subsystems, **built and tested as isolated units, shipped
together**. Build order: **C → A → B** (C is the safety gate we then use to ship v0.1.8 itself;
A is the free "wow"; B is monetization, which reuses A's report helper). Pre-traction, solo
founder, no users yet. Council flagged over-bundling — mitigated by building each unit green
independently before they ride out together.

---

## C — Beta-feed release gate

**Why:** Today, tagging a release auto-promotes it live to everyone via OTA with no QA hold
(v0.1.7 went straight live). C adds a hold so future releases are tested on the real signed
build before reaching stable users.

**Behaviour:**
- New setting **"Get pre-release updates"** (default **OFF**). NP turns it ON to be the beta tester.
- A tagged release publishes to a **beta feed** first; stable users don't see it until a manual
  **promote** step.
- Updater checks the **beta** feed when the toggle is ON, **stable** when OFF.
- v0.1.8 itself ships through this gate: tag → beta → NP QAs the signed build → promote.

**Mechanism (resolve at build time, prefer the simplest that works):**
- Approach: publish the release as a GitHub **prerelease**; `releases/latest/download/latest.json`
  (the stable updater endpoint) ignores prereleases, so stable stays put. Beta-opted apps point
  at an endpoint that includes the prerelease (a `latest-beta.json` asset on a fixed feed, or the
  prerelease tag's asset). **Promote** = un-mark prerelease (it becomes the latest release) so the
  stable endpoint now serves it.
- App side: the updater endpoint is chosen at runtime from the toggle. Tauri v2 updater supports
  configuring/overriding endpoints; the toggle selects stable vs beta URL.
- CI: the release workflow keeps building on tag `v*`; add a job/step to also emit/maintain
  `latest-beta.json`, and keep stable `latest.json` un-promoted until the manual promote.

**Files:** `.github/workflows/release.yml` (beta json), `ui` settings + updater wiring,
`ops/docs-internal/RELEASE_QA.md` (already documents the flow).

**Tests:** updater endpoint selection by toggle (unit); manual: tag → only beta apps update →
promote → stable apps update.

## A — Premium report everywhere (served reports + report-v2)

**Why:** Reports open as `file://`, so Safari (Mac default) blocks citations from opening source
PDFs. And the gorgeous report-v2 design isn't yet in the engine helper.

### A1 — Served reports (the Safari fix)
- The FastAPI sidecar (already on `127.0.0.1:8765`) **serves the library root over http**, via a
  route that is **path-restricted to the configured library directory** (no traversal, serves
  only within the library — security-reviewed).
- The app **detects** generated reports by scanning each company's `research_report/` folder.
- In the **Library view**, a company that has a report shows an **"Open report"** action → opens
  `http://127.0.0.1:8765/<lib-path>/research_report/business_model.html` in the **default browser**.
- Because it's http (not file://), citations (relative `../…pdf#page=N`) open in **every browser,
  Safari included**. This is the proper fix for the v0.1.7-era Safari citation bug.

**Design notes:**
- Reports are generated *outside* the app (user's Claude/Codex writes the HTML). The app only
  detects + serves + opens them; it never generates them.
- Serve route validates the requested path resolves *inside* the library root (reject `..`).
- "Open report" surfaces per-company (latest report). A full cross-company "Reports" view is a
  later add (not in v0.1.8).

### A2 — Report-v2 folded into the helper
- Replace the static template in `engine/report_helper.py` `_TEMPLATE` with the **Direction-C
  dynamic v2**: dark masthead, provenance header (sources + dates + covered/excluded), one-line
  thesis, numbered key findings, inline **SVG narrative chart** (revenue bars + EBITDA-margin
  line, drawn from `data-*` attributes, no libraries), **fact-vs-analysis** visual separation,
  sticky context bar, collapsible sections, reading-progress bar, **Safari-safe citation handler**
  (try new tab → fall back to same-tab; never leave a dead window swallow the click).
- The v2 source is in `design-mockups/report-v2-direction-c.html` (gitignored) — port verbatim
  into the helper template, parameterised for any company.
- Update the Business Model Brief skill to populate the chart `data-*` (revenue/margin arrays) and
  the provenance block; degrade gracefully (omit the chart) if the data isn't available.

**Files:** `engine/report_helper.py`, `engine/library.py` (serve route may live in `api/`),
`api/routes.py` (static serve), `ui` Library view ("Open report"), the skill `.md`.

**Tests:** helper contains v2 markers (chart, provenance, fact/analysis) — extend
`test_report_helper.py`; serve route rejects path traversal + serves in-library files (api test);
UI shows "Open report" when a report exists.

## B — Monetization: in-app paywall + first paid skill

**Why:** Turn on revenue with the first paid skill (Concall Decoder, ₹3,000), delivered through a
seamless in-app flow that feels integrated and never strands a buyer.

### B1 — The seamless purchase flow (no leaving the app)
1. Premium skill in the Skills overlay shows **"Get ₹3,000"**.
2. Click → an **in-app payment window** (Tauri webview) opens **Instamojo's secure checkout**
   *inside FilingForge* (not a jump to Safari). Buyer pays by UPI/card.
3. On success, Instamojo redirects to our **return URL**; the app detects that navigation →
   closes the window → calls the Worker `/redeem` → writes the watermarked `.md` into
   `~/.filingforge/skills/` → toast **"Concall Decoder added ✓ — Use it now."**

### B2 — The server (Cloudflare Worker + KV, free tier)
- `POST /webhook/instamojo` — on payment, Instamojo POSTs here; **verify the webhook signature
  (salt)**; record `{code, skill_id, version, email, name, phone, purchase_id, paid_at,
  activations:0}` in KV. **This is the source of truth** — recorded the instant payment clears.
- `POST /redeem` — body `{code}`; validate; enforce a sane **activation cap (e.g. 3 devices)**;
  inject the buyer's **email watermark**; return the **current version** of the `.md`.
- `GET /skills-manifest` — returns `{skill_id: latest_version}` for the in-app update check.
- Skill `.md` sources live in the Worker/KV (private; never in the public repo).

### B3 — Fail-safes (a payment never strands a buyer)
- **Three delivery paths:** (1) seamless in-app; (2) **"Redeem code"** field — paste the code from
  Instamojo's email; (3) existing **"Import a skill"** file picker. **No drag-and-drop** (cut per NP).
- **Re-fetchable purchase** (not single-use) up to the activation cap → reinstall / new machine
  recovers the purchase.
- **Worker down at redeem** → "Your purchase is safe — your code's in your email; we'll install
  when you reconnect." Payment recorded at Instamojo + KV; delivery retries forever.
- **Email delivery (Instamojo auto-deliver on payment):** the **`.md` file** (generic, owner's
  copy + ultimate fallback) + a **`HOW-TO.md`** (what it does, install, run in Claude/Codex,
  re-import anytime) + receipt + redeem code. Reduces support; buyer is self-sufficient.
  - Trade-off accepted: the emailed `.md` is **un-watermarked** (Instamojo sends a static file);
    the **app/Worker-delivered copy is watermarked**. Watermark = soft deterrent, not a hard lock.

### B4 — Skill updates ("includes updates" made real)
**Launch needs only the cheap half.** We won't ship a Concall Decoder update on day one, so the
fancy in-app auto-update is **not a v0.1.8 blocker** — but the design is in place so we're never stuck.

**Build at launch (free — the promise is deliverable):**
- Each skill `.md` carries a **version** (`filingforge_skill: <ver>`). The Worker always serves the
  **latest** version for a valid code → "update" = re-redeem; no new infra (redeem already exists).
- **Email path:** NP emails the customer list (name+email from purchases) the new file when an
  update ships. Covers any early update with zero app work.
- **No re-payment** — buy once, owned forever, updates free.

**Defer until the first real update ships (optional, not launch-critical):**
- `GET /skills-manifest` (latest versions) + the app's daily check comparing installed vs latest →
  **"Update available"** badge → one-click re-redeem. Privacy: folded into the existing daily ping
  (availability only, not usage telemetry). Build this when there's actually an update to push.

### B5 — In-app store affordance
- Skills overlay: premium skills show **"Get ₹<price>"** (→ B1 flow) instead of "Use".
- A small **"Redeem code"** entry (for the email-code fallback).
- Owned premium skills behave like any imported skill ("Use").

### B6 — Customer data + policies
- **Instamojo handles** payment, all card/UPI credentials (we never see them), and the receipt email.
- **We receive** (webhook + dashboard): name, email, phone, amount, product, purchase_id, timestamp
  = the customer list (updates, support, watermark). This is **purchase data**, not app telemetry —
  does not touch the no-app-telemetry promise.
- **Policies** (drafted, to publish): **Refund** ("all sales final — digital goods delivered
  instantly, no refunds; contact support if it won't install"), **License** ("personal-use license,
  don't redistribute/resell; updates included"), **Privacy** ("name+email for purchase + updates;
  Instamojo processes payment; app sends no usage data"). Placed on: Instamojo product page +
  account policy fields + website `/refunds` `/privacy` `/terms` + the delivery email.

**Files:** new Cloudflare Worker repo/dir (private), KV; `ui` SkillsOverlay (Get/Redeem/payment
webview), payment-success detection; the `concall-decoder.md` + `HOW-TO.md` content (private);
website policy pages; Instamojo product config (NP does account/KYC + paste config).

**Tests:** Worker — webhook signature verify, redeem validates + caps + watermarks + serves latest
(unit); app — redeem-code path installs; payment-success detection closes window + installs;
update-available surfaces when manifest version > installed.

### Division of labour for B
- **NP:** create Instamojo account + KYC (sole-prop, PAN+bank); create the ₹3,000 product; upload
  `.md`+`HOW-TO.md`; paste description + policies; set redirect URL + webhook + salt; test payment.
- **Claude:** all code (Worker + app), all copy (`concall-decoder.md`, `HOW-TO.md`, policies,
  website pages), exact URLs/salt-field instructions for NP to paste.

## Cross-cutting

- **Release:** ship all three via the **beta gate** (C): tag v0.1.8 → beta → NP runs the 5-point QA
  on the signed build (+ the new paths: open-report-in-Safari, a test purchase end-to-end,
  beta→promote) → promote → live.
- **Privacy invariant:** the app still sends no *usage* telemetry. The only new network calls are:
  the daily app+skill update check (availability only) and the one-time purchase/redeem (a
  commercial transaction). Both are transparent and non-usage.
- **No-DRM-to-run invariant:** a skill, once installed, runs fully offline forever. The Worker is
  touched only at purchase, redeem, and update-check — never at run time.
- **Deferred to later:** full cross-company "Reports" view; hard licensing / per-device blocking
  (arrives with Pro/MCP, which needs the server anyway); MCP; enterprise.

## Build order & isolation
1. **C** (beta gate) — smallest; lets us ship v0.1.8 safely.
2. **A** (served reports + report-v2) — the free "wow"; A2 helper is reused by B's skills.
3. **B** (paywall + Concall Decoder) — depends on A's helper for the paid skill's output.

Each unit: green tests independently → bundle → ship via beta gate.
